# AI Agent 요구사항

요구사항 ID: **AI-001**<br>
상태: **방향 승인 — 세부 계약과 기준값은 3주 로드맵에서 확정**<br>
도메인 담당자: **AI 기능 담당자**

## 1. 목적

은퇴 설계 상담에서 대화 문맥, 현재 화면, 저장된 고객 정보, 검토된 금융 지식을 함께 사용해 답변하고, 필요한 경우 안전한 화면 변경을 제안하는 AI Agent를 제공한다.

## 2. Agent 구성

| Agent | 사용자 관찰 가능 책임 | 금지·경계 |
|---|---|---|
| QA | 질문에 답하고 근거가 필요한 금융 사실에 출처를 제시 | 근거 없는 수치·상품 추천·수익 보장 금지 |
| 입력 보조 | 발화에서 폼 필드와 값을 추출·정리해 변경안을 제안 | 사용자 승인 전 저장 금지 |
| 에러 검토 | 결정론적 검증 결과를 설명하고 수정 방법을 제안 | LLM 단독으로 유효성 판정 금지 |
| 차트 분석 | 구조화된 차트 원본 수치와 계산 결과를 개인 상황에 맞게 설명 | 화면 이미지 추측과 원본에 없는 수치 생성 금지 |
| 정성정보 유도 | 누락된 목표·가치관·걱정을 한 항목씩 멀티턴으로 질문 | 이미 답한 정보 반복 질문과 무한 질문 금지 |
| fallback | 모호한 의도, 지원 범위 밖 요청, 시스템 오류에서 안전하게 복구 | 전문 답변이나 데이터 변경을 가장하지 않음 |

6개 Agent의 채택 근거와 구조적 제약은 [`ADR-0001`](../decisions/0001-six-agent-ai-architecture.md)을 따른다.

## 3. 공통 사용자 흐름

1. 사용자가 현재 단계에서 메시지를 보낸다.
2. Django가 인증·세션을 확인하고 저장 데이터와 현재 폼을 조합한다.
3. AI 라우터가 실제 `step_id`, 메시지, 대화 문맥을 바탕으로 6개 Agent 중 하나를 선택한다.
4. 선택된 Agent가 RAG 또는 허용된 도구가 필요한지 판단한다.
5. Agent가 자연어 답변과 구조화된 부가 결과를 생성한다.
6. 데이터 변경안은 화면에 제안으로 표시하고 사용자가 승인하거나 거절한다.
7. 성공·실패·평가·도구 호출 결과를 감사 가능한 형태로 남긴다.

## 4. 공통 기능 요구사항

### AI-CTX — 대화 문맥

- 같은 `thread_id`의 필요한 이전 발화와 확정 고객 정보를 사용한다.
- 다른 사용자나 상담 세션의 문맥을 사용하지 않는다.
- 사용자가 이전 정보를 수정하면 최신 확정값을 우선한다.
- 문맥 길이가 예산을 넘으면 정의된 요약·절단 정책을 적용한다.

### AI-ROUTE — 의도와 단계 라우팅

- 프론트의 실제 `step_id` 전체를 인식한다.
- Agent 후보는 단계 allowlist와 사용자 의도를 함께 사용해 제한한다.
- 모호한 경우 임의 처리하지 않고 정성정보 유도 또는 fallback으로 보낸다.

### AI-UI — 인터페이스 상호작용

- AI 결과는 자연어 응답과 구조화된 `FormUpdateProposal`을 구분한다.
- 필드명·자료형·단위·제약은 공통 필드 레지스트리를 따른다.
- Backend가 변경안을 재검증하고, 사용자가 승인한 뒤에만 저장한다.
- 구현 순서는 `basic-info`(단일 필드), `financial-mindset`(정성 텍스트), `financial-assets`(반복 목록)로 공통 구조를 먼저 검증한 뒤 나머지 단계로 확장한다.
- 이 순서는 최종 지원 단계를 세 가지로 제한하지 않는다. 1주차에 모든 실제 단계와 필드 계약을 먼저 확정한다.
- `financial-goals`의 중첩 목록과 차트 단계의 읽기 전용 분석 payload는 별도 계약 테스트를 둔다.

### AI-KNOWLEDGE — 전문 지식과 도구

- 운영 RAG 문서는 출처, 발행기관, 기준일, 버전, 적용 범위, 검토자를 가진다.
- 근거가 필요한 답변은 사용한 문서와 근거 구간을 표시한다.
- MCP·Function Calling 도구는 allowlist, 입력 스키마, timeout, 오류, 권한, 감사 계약을 가진다.
- 금융 계산은 가능한 한 결정론적 도구가 수행하고 LLM은 선택·설명 역할을 맡는다.

### AI-FAILURE — 실패와 복구

- LLM·RAG·MCP·DB·SSE terminal 실패를 성공으로 표시하지 않는다.
- 재시도는 횟수와 대상 오류를 제한하고 같은 부작용을 중복 적용하지 않는다.
- 사용자에게 실패 원인 범주와 가능한 다음 행동을 이해하기 쉽게 안내한다.

## 5. 3주 인수 조건

아래 기준은 1차 baseline 결과로 조정할 수 있으나, 조정 근거와 승인자를 남긴다.

| 영역 | 초기 완료 기준 |
|---|---|
| Agent 구성 | 6개 Agent 각각 대표 성공·실패 경로 자동 테스트 보유 |
| 문맥 | 3~5턴 시나리오 30개 중 90% 이상 통과, 세션 간 유출 0건 |
| 라우팅 | 실제 단계·의도 평가셋에서 정확도 95% 이상 |
| 입력 보조 | 대표 세 형태의 필드·자료형·단위 exact match 90% 이상, 미승인 저장 0건 |
| RAG | Recall@5 85% 이상, MRR@5 0.70 이상, 인용 포함률 90% 이상 |
| 운영 | SSE terminal 완료율 99% 이상, Agent·검색·도구별 지연·비용 측정 가능 |
| 보안 | 치명적 공격 성공 0건, 세션 간 정보 유출 0건, trace의 마스킹 대상 원문 노출 0건 |
| AX | 폼 완료 시간, 제안 승인·수정·거절률, 완료 턴 수의 baseline 확보 |

## 6. 범위 참조

3주 MVP의 포함·제외 범위는 [프로젝트 요구사항](../REQUIREMENTS.md) §4만 따른다. 기능 문서에서는 같은 목록을 다시 정의하지 않는다.

## 7. 의존성과 열린 결정

- Backend·Frontend 담당자와 공통 필드·API·승인 계약을 1주차에 동결해야 한다.
- 도메인 담당자가 RAG 문서의 출처·기준일·정확성을 승인해야 한다.
- 모델 provider, 평가 비용 예산, 운영 지연 SLO는 baseline 후 확정한다.
