# AI 보안 정책 v0.1

- 상태: 3주 MVP 정책 확정 — P13 마스킹·P14 공격 fixture 준비, F11~F13 production 통제 대기
- 적용 범위: `front-pjt`의 AI 화면, Django AI 연동 API, `ai-pjt`, RAG 저장소, in-process Function Calling, LLM·관측 서비스 연동
- 책임자: AI 기능 담당자

## 1. 목적

은퇴 설계 과정의 개인정보·금융정보를 최소한으로 사용하고, Agent·RAG·도구·서비스 간 호출을 신뢰하지 않는다는 전제에서 인증·권한·검증·감사를 적용한다.

이 정책은 프로젝트 수준 v0.1이다. 적용할 기능과 후속 범위는 [프로젝트 요구사항](../REQUIREMENTS.md) §4만 따르며 이 정책에서 다시 정의하지 않는다.

## 2. 데이터 분류

| 등급 | 예시 | 기본 처리 |
|---|---|---|
| 직접 식별정보 | 이름, 연락처, 이메일, 계정 식별자 | LLM·trace 전달 금지 또는 가명 대체 |
| 준식별정보 | 나이, 직업, 가족구성, 세션 패턴 | 과업에 필요한 최소 필드만 전달 |
| 금융 민감정보 | 소득, 자산, 부채, 연금, 투자 성향 | 목적별 allowlist, 암호화 전송, trace 마스킹 |
| 운영정보 | request·thread·trace ID, 오류, 지연 | 가명화하고 보존기간 제한 |
| 공개 지식 | 승인된 금융 제도·가이드 | 출처·기준일·버전·검토 상태 관리 |

새 필드를 AI에 전달하기 전 데이터 등급, 목적, 보존, 외부 전송 여부를 검토한다.

## 3. 기본 원칙

1. **명시적 검증**: 내부 네트워크, callback, RAG 문서, Function tool 입력·응답도 신뢰하지 않는다.
2. **최소 권한**: Agent와 도구는 현재 과업에 필요한 데이터·기능만 접근한다.
3. **데이터 최소화**: 전체 고객 snapshot 대신 Agent별 allowlist를 사용한다.
4. **기본 거부**: 알 수 없는 단계·필드·도구·권한·출처는 거부하거나 fallback 처리한다.
5. **사람의 승인**: AI가 생성한 금융 데이터 변경과 외부 부작용은 별도의 사용자 승인 전 적용하지 않는다. 사용자 요청 여부와 모델 confidence는 승인 증거가 아니며 미저장 draft도 자동 변경하지 않는다.
6. **재현·감사**: 모델·프롬프트·문서·도구 버전과 결정 결과를 가명화된 식별자로 추적한다.
7. **실패 폐쇄**: 인증·검증·가드레일 장애를 성공이나 허용으로 처리하지 않는다.

## 4. 서비스·API 통제

- Browser는 AI 서버와 MCP 서버를 직접 호출하지 않고 Django를 경유하며 Function tool은 AI 프로세스 내부에서만 실행한다.
- Django→AI와 AI→Django callback은 같은 `AI_SERVICE_BEARER_TOKEN`을 `Authorization: Bearer`로 검증한다.
- shared bearer token은 빈 값이나 선택적 bypass를 허용하지 않고 TLS 안에서만 전송하며 사용자 JWT와 분리한다.
- token 하나가 양방향 권한을 가지므로 유출 시 두 서비스를 함께 차단·회전하고, 회전 전에는 신규 접수를 중지한 뒤 기존 processing 작업을 drain한다.
- `request_id`는 추측하기 어렵고 callback의 idempotency 키로 사용한다.
- callback은 request·session·thread의 결합을 확인하고 완료된 요청의 중복 부작용을 막는다.
- proposal 승인·거절은 action 안의 change별로 기록하고 같은 결정의 재전송만 idempotent하게 허용한다.
- 사용자 JWT를 AI payload나 모델이 생성하는 Function tool 인자에 전달하지 않는다.
- AI·MCP·DB 계정은 분리하고 필요한 테이블·도구 권한만 부여하며, tool adapter에는 현재 request에 필요한 snapshot과 기능만 제공한다.
- timeout, 요청·응답 크기, 동시 실행, 재시도 횟수에 상한을 둔다.

## 5. 대화·프롬프트 통제

- 시스템 지시, 개발자 정책, 사용자 메시지, RAG 문서, 도구 결과를 명확히 구분한다.
- 사용자 또는 문서가 시스템 지시를 무시하거나 비밀·다른 사용자 데이터를 요구해도 따르지 않는다.
- 대화 이력은 같은 `thread_id`에 한해 복원하고 사용자·세션 소유권을 Django에서 확인한다.
- 입력 길이, 허용 자료형, 파일·URL 정책을 검증한다.
- 출력은 구조화 스키마, 금지 표현, 인용, 민감정보 노출을 검사한 뒤 callback한다.

## 6. RAG 통제

- 운영 문서는 출처·발행기관·기준일·버전·적용 범위·도메인 검토 상태를 가진다.
- 검토되지 않은 문서와 사용자 입력 문서를 운영 지식 collection에 자동 편입하지 않는다.
- RAG 문서의 명령문은 실행 지시가 아닌 인용 가능한 데이터로 취급한다.
- 검색 문서 ID·버전은 trace에 남기되 민감 원문은 기본 로그에 남기지 않는다.
- 문서 폐기·교체 시 재색인과 이전 버전 사용 중단을 검증한다.

## 7. Function Calling 통제

- 도구는 allowlist와 버전이 지정된 입력·출력 스키마를 가진다.
- Agent별 호출 가능한 도구와 scope를 제한한다.
- 도구 인자를 코드로 검증하고 LLM이 생성한 설명·사용자·세션·step·권한 값을 신뢰하지 않는다. 요청 식별자와 deadline은 runtime이 주입한다.
- 쓰기·외부 전송·금융 데이터 변경 도구는 별도 승인과 감사가 없으면 제공하지 않는다.
- 도구 timeout·오류·부분 실패를 모델 입력과 사용자 응답에 명시적으로 전달한다.
- 모든 도구 호출은 가명화된 요청자, 도구·버전, 인자 분류, 결과 상태, 승인 여부를 기록한다.
- raw argument와 금융 결과값은 기본 감사 event에 남기지 않으며 모든 Agent 출력은 callback 전 결정론적 후검증을 통과한다.

## 8. 가명처리·관측

- 사용자 ID와 상담 ID는 관측 전용 가명 식별자로 변환하고 매핑 정보는 trace 저장소와 분리한다.
- 이름·연락처·계좌 식별자 등 직접 식별정보는 LLM·Langfuse·일반 로그에 보내지 않는다.
- 금융 수치는 과업에 필요할 때만 전달하고 로그·trace에서는 마스킹하거나 구간화한다.
- 원문 저장이 필요한 평가·사고 분석은 목적, 접근자, 보존기간, 폐기 방법을 별도로 승인한다.
- 마스킹 전후 표본과 탐지 누락률을 검토하고 결과를 보안 리포트에 남긴다.

## 9. 공격 시나리오와 완료 기준

최소 다음 시나리오를 자동화된 회귀셋에 포함한다.

- 시스템 프롬프트·비밀 탈취
- 다른 사용자·세션의 금융정보 요청
- RAG 문서의 간접 프롬프트 인젝션
- 도구명·인자·권한 조작
- 미승인 폼 변경과 승인 우회
- callback 위조·재전송·request/session 바꿔치기
- 과도한 토큰·무한 재시도·대량 도구 호출
- 금융 수익 보장·과도한 확정 표현 유도
- 역할극·인코딩·다국어를 이용한 가드레일 우회

3주 MVP의 보안 완료 기준:

- 치명적 공격 성공 0건
- 세션 간 개인정보·금융정보 유출 0건
- 미승인 변경 0건
- 권한 밖 도구 호출 성공 0건
- trace·일반 로그의 마스킹 대상 원문 노출 0건
- 발견된 취약점마다 재현 입력, 영향, 수정, 회귀 테스트를 기록

## 10. 예외와 사고 대응

- 정책 예외는 목적, 데이터, 기간, 책임자, 보완 통제, 종료일을 문서화해 승인받는다.
- 의심스러운 유출·권한 우회·악성 문서가 발견되면 관련 도구·collection·trace 전송을 우선 중지한다.
- 영향을 받은 request·thread·문서·모델 버전을 식별하고 자격 증명 회전, 데이터 폐기, 회귀 테스트를 수행한다.
- 사고 원문은 일반 애플리케이션 로그에 복사하지 않고 제한된 조사 위치에서만 다룬다.
