## 1. 목적과 작업 경계

기존 저장 데이터에서 [내부 모델](../models.py)의 `RetirementProfile`과
`SimulationAssumptions`를 만들기 위한 변환·거절 규칙이다. 계산식과 MC/What-if 엔진을
다시 만들지 않는다. [서비스 연결 설계](service-integration-design.md)의 2단계에 해당한다.

사용자는 실행 위치를 **BE 직접 실행**으로 선택했다. 향후 흐름은 다음과 같다.

```text
BE: 인증·상담 소유권·일관된 저장 snapshot 확보
  → 독립 패키지: 입력 매핑 → 기존 MC/What-if → 결과 변환
  → BE 응답 → 보고서 시뮬레이션 화면
```

최초 규격 커밋 `232a0fc`는 모듈 안의 문서만 변경했다. 후속 어댑터·기본 테스트도
`ai-pjt/retirement_simulation/` 안에서만 구현한다. BE·FE·Agent·컨텍스트·
매뉴얼·공통 서버·DB·Docker·의존성·Jira는 변경하지 않는다. BE 실행을 선택한 것이
그 영역의 변경 승인이나 다른 담당자의 합의를 뜻하지 않는다. 단일 소스 패키지 배포,
BE API·snapshot 일관성·실행 한도는 후속 연결 작업이며 AI 서버 진입점은 추가하지 않는다.

`build_customer_info()`는 **형태를 확인하는 참고 원천**이지 모듈의 의존 함수가 아니다.
입력은 그 반환값 전체가 아니라 내부 `saved_data`에 대응하는 서버 제공 mapping이다.
모듈에서 Django·serializer·AI 호출부를 import하거나 DB를 조회하지 않는다.
미저장 `current_form`, AI 변경 제안, 대화 컨텍스트를 병합하지 않는다.

현재 `saved_data`에는 다음 정보가 없다.

- 목록이 빈 이유가 미입력인지 실제 자산/연금 없음인지 확인한 근거.
- 상담 소유권·인증 결과, 전체 재무정보의 동일 시점/버전 보장.
- 포트폴리오의 연 수익률 평균·변동성·물가를 묶은 서비스 가정 설정.

`get_section_completion()`은 주로 관련 행의 존재를 확인하고 `is_ready_for_reports()`는
그 결과를 모두 만족하는지 본다. `completed` 상태만으로 nullable 값·기간 정합성을
신뢰하지 않는다. `refresh_completion_status()`는 저장 동작이므로 어댑터에서 호출하지 않는다.

## 3. 입력 경계·누락·원본 보존

초기 어댑터는 저장형 mapping과 별도 계산 가정, 필요한 경우 서버가 확인한
빈 목록 근거를 받는 순수 함수다. `map_retirement_profile()`은 `ProfileMappingResult`,
`map_simulation_assumptions()`는 기존 `SimulationAssumptions`를 반환한다.
이 문서의 논리 입력은 새 HTTP 필드가 아니다.

| 입력 종류 | 규칙 |
|---|---|
| `basic_info` | 필수 객체. 나이 3개는 필수 정수 |
| `financial_assets`, `pension_assets`, `goal_periods` | 필수 배열. 행은 객체. 누락/null을 빈 배열로 만들지 않음 |
| `real_estate_assets`, `liabilities`, `goal_milestones` | 미지원 조건 존재를 확인할 필수 배열. 누락 시 반영 범위를 확인할 수 없으므로 오류 |
| 그 밖의 저장 필드 | 고객 설명·이름·상품명·시간·소득/현재 지출 등을 계산에 사용하지 않음. 저장형 snapshot의 추가 필드는 허용하되 결과에 통째로 복사하지 않음 |
| 금액 | 0 이상 정수 KRW. `0`은 유지. null·키 누락·bool·문자열·실수·음수는 필요한 계산 필드에서 오류 |
| 배열 행 ID | 저장 serializer의 `id`는 있어도 계산 모델에는 넣지 않음. 있으면 양의 정수인지 검증하고 같은 원천 목록 내 중복 ID는 오류. 목표 항목 ID는 목표 기간 전체에서 중복 검사 |
| 순서·원본 | 정렬·합산·변환은 새 객체에서 수행. 입력 dict/list 및 기존 프로필을 변경하지 않음 |

### 빈 목록과 명시적 0

`financial_assets=[]` 또는 `pension_assets=[]`만 전달하면 **없음 확인 부족**으로 거절한다.
별도 내부 입력 `confirmed_empty_sections`로 해당 섹션의 없음이 확인됐다는 근거를
전달할 수 있도록 구현한다. 문자열 list/tuple로 받고 허용 이름은 `financial_assets`,
`pension_assets` 두 개이며 기본값은 빈 tuple이다. 이름 오류·중복·비어 있지 않은 목록과의 모순은 거절한다.
호출자가 임의로 전부 확인 처리하거나 브라우저 값을 그대로 신뢰해서는 안 된다.
실제 서비스에서 이 근거를 어떻게 얻을지는 D4의 남은 연결 결정이다. 현재 DB에
이 필드가 저장돼 있거나 기존 완료 상태에서 자동 추출할 수 있다는 뜻이 아니다.

- 없음이 확인된 금융자산 목록: `liquid_assets=0`, `monthly_savings=0`.
- 없음이 확인된 연금 목록: `pension_incomes=()`.
- 금융자산 행의 `monthly_savings=null`: 선택 입력이어도 0으로 바꾸지 않음.
- `goal_periods=[]` 또는 은퇴 후 구간 없음: 없음 확인으로 우회할 수 없는 생활비 부족.
- 생활비 0원: 유효한 구간에 `items=[{"amount": 0}]`처럼 명시한다.

빈 목록 확인은 전체 상담 완료/소유권을 증명하지 않는다. 내부 검증과 서비스의
보고서 진입 조건은 별개다. 기존 보고서 준비 조건은 금융자산·연금·부동산 등의
행 존재를 요구하므로, 모듈의 자산/연금 없음 지원이 곧 현재 보고서 UI에서의 접근
지원은 아니다. 이 차이를 해결하려고 BE 완료 조건이나 가짜 자산 행을 추가하지 않는다.

## 4. 프로필 매핑

### 4.1 나이

| 내부 필드 | 저장 원천 | 검증 |
|---|---|---|
| `current_age` | `basic_info.age` | 정수 18~100 |
| `retirement_age` | `basic_info.retirement_age` | 정수 18~100 |
| `end_age` | `basic_info.end_age` | 정수 18~120, 현재/은퇴 나이 이상 |

기본값이나 생년월일 추정은 없다. 내부 모델은 과거 은퇴와 종료 나이=은퇴 나이를
허용한다. 반면 BE 쓰기 serializer는 은퇴 나이<현재 나이, 종료 나이<=은퇴 나이를
거절한다. 어댑터는 내부 엔진 범위를 유지하고 이 차이를 문서화한다. 내부 합성/과거
입력 테스트가 통과해도 기존 폼에서 그 값을 새로 저장할 수 있다고 설명하지 않는다.

### 4.2 유동 금융자산·월 적립

`asset_type`은 문자열 양 끝 공백만 제거해 비교하며 다음 세 범주로 구분한다.

| 분류 | 매핑 처리 |
|---|---|
| `예금/적금`, `주식`, `펀드/ETF`, `채권`, `가상자산` | 기존 5종. 평가액과 월 적립액을 검증하고 합산 |
| `기타` | 인식하지만 모델링하지 않음. 해당 행의 평가액·월 적립액을 모두 제외하고 행별 안내 생성 |
| 그 밖의 문자열·null·빈 문자열·문자열이 아닌 값 | `unsupported_value`. 필드 자체 누락은 기존 `missing_field` |

상품명이나 BE 키워드 분류로 추정하지 않는다. `기 타`, `기타자산`, 직접 입력한 상품명 등을
`기타`로 치환하지 않는다. 기존 5종도 모든 해당 상품의 유동성·시장위험을 검증한 목록은 아니다.

```text
liquid_assets   = 모델링하는 5종 금융자산 행의 current_value 합계
monthly_savings = 같은 행의 monthly_savings 합계
```

두 금액은 **모델링하는 행마다 필수**다. 평가액이 0인 행도 적립액을 보존한다. `principal` 대체,
목적별 필터, 소득-지출 잉여 재합산, 연금계좌 잔액·적립액 합산은 하지 않는다.
실물자산·비유동 상품을 금융자산으로 입력한 행을 조용히 합산하지 않는다.
지원 행은 하나의 유동 포트폴리오로 단순화하며 자산군별 수익률·환금성·상관관계는
모델링하지 않는다는 범위 안내를 항상 결과에 남긴다.

`기타`는 유동성·수익 특성을 이 분류만으로 결정할 수 없으므로 별도 수익률이나 현금흐름을
생성하지 않는다. 각 제외 행에 `other_financial_asset_not_modeled` 안내와
`financial_assets[N]` 경로를 남긴다. `N`은 0부터 시작하는 **원본 배열 위치**이며 DB ID나
제외 후 재정렬한 위치가 아니다. 이름·금액 원문은 안내에 넣지 않는다.

부동산 등 기존 미모델링 범주처럼 `기타`의 사용하지 않는 금액 필드는 읽거나 수치 검증하지
않는다. 누락·null을 0으로 보충하는 것이 아니라 **그 행 전체를 합산 대상에서 제외**하는 것이다.
행의 mapping 구조·필수 `asset_type`·존재하는 ID의 자료형/범위·중복 검증은 그대로 수행한다.
이는 제외된 금액의 저장 유효성을 승인하는 것이 아니며, 다른 모델링 행의 필수 금액 검증은 유지한다.

모든 금융자산이 `기타`이면 모델링 자산·적립 합계는 0이지만 원본 목록은 비어 있지 않다.
`confirmed_empty_financial_assets`를 생성하지 않으며 `confirmed_empty_sections`에
`financial_assets`를 넣으면 기존 모순 확인 오류가 난다. 실제 빈 목록 `[]`의 명시적 없음 확인
규칙도 바뀌지 않는다. 입력 목록·원본 금액은 삭제하거나 변경하지 않는다.

MC와 What-if는 이 매핑 결과를 기준으로 사용한다. What-if의 `monthly_savings`를 명시하면
기존 계약대로 **변경 후 총 월액**으로 대체하며 제외한 행의 적립액을 자동으로 다시 더하지 않는다.

### 4.3 은퇴 후 월 생활비

1. `phase`는 `before`/`after`만 허용한다. `before`는 은퇴 후 생활비로 사용하지 않으며
   소득/현재 지출과 함께 은퇴 전 현금흐름을 재계산하지 않는다는 범위 안내를 남긴다.
2. 각 `after` 행의 `from_age`, `to_age`는 양 끝 포함 1~120, 시작<=끝이다.
   `items`는 비어 있지 않은 배열이어야 하며 모든 항목의 `amount`가 필수다.
3. **같은 기간 내부의 항목들만** 합산해 `monthly_amount`로 만든다.
   이름/고정 여부로 일부 항목을 빼지 않는다. `is_fixed`는 별도 물가율을 뜻하지 않는다.
4. 구간을 시작 나이로 정렬하고 서로 다른 `after` 구간이 한 살이라도 겹치면 거절한다.
   `60~75`와 `75~90`은 오류, `60~74`와 `75~90`은 정상이다. 끝을 임의로 줄이거나
   같은 금액의 기간을 병합·평균·중복 제거하지 않는다.
5. `max(current_age, retirement_age)`부터 `end_age`까지 빠짐없이 덮어야 한다.
   현재 계산 범위 밖의 유효한 `after` 구간도 보존하고 중복을 검사한다. 후속 조기 은퇴
   What-if에서 사용할 수 있으므로 기준 실행에 불필요하다고 잘라내지 않는다.
6. 원천 금액은 현재 나이 기준 월 금액으로 취급한다. 12배나 물가 상승을 미리 적용하지
   않는다. 연 금액·물가 적용은 기존 현금흐름 엔진이 한 번만 수행한다.

BE 기간 쓰기는 시작<끝을 요구하지만 내부 모델은 한 살짜리 구간도 허용한다.
이 차이도 나이 규칙과 마찬가지로 BE 변경 없이 내부 경계 테스트로 구분한다.
개별 항목 금액만으로 생활비의 현실적 충분성을 판단하지 않는다.

### 4.4 월 연금 수령 일정

`receive_method`는 양 끝 공백 제거 후 `연금형`만 지원한다. `일시금`은 월 현금흐름으로
변환할 수 없으므로 미지원 오류, null/빈 값은 필수 입력 부족이다.
`pension_start_age`는 내부 일정의 나이 범위 1~120인 정수, `expected_amount`는
명시된 0 이상 정수 원/월이다. BE 쓰기의 개시 나이 제한은 55~80으로 더 좁다.
상품명·가입일·납입기간·현재 나이로 월 수령액을 추정하지 않는다.

| `pension_period` 입력 | 변환 |
|---|---|
| 양 끝 공백 제거 후 `종신` | 계산용 종료 나이=`profile.end_age`. 실제 수명 예측이 아님 |
| ASCII 정수 `N년`, N=1~120, 선행 0 없음 | 실제 종료 나이=`pension_start_age + N - 1`, 계산용 끝은 계획 종료 나이와의 최솟값 |
| `기타`, `10`, `10~20년`, `0년`, `01년`, `10 년`, null 등 | 불명확/미지원 기간 오류. 임의 종신 처리 금지 |

기간 문법은 전체 문자열 `[1-9][0-9]{0,2}년` 일치 후 N 범위를 검사한다.
BE 모델의 `payment_period_years`는 **납입기간**이므로 수령기간으로 사용하지 않는다.
계획 종료 이후까지 받는 부분은 계산 범위 밖이라는 안내와 함께 자른다.
수령이 현재 전에 모두 끝났거나 계획 종료 뒤에 시작하면, 필수 필드/문법 검증 후
활성 일정에서 제외하고 범위 밖 연금 안내를 남긴다. 종료<시작인 `PensionIncome`을
만들지 않는다. 예: 65세부터 10년이면 65~74세, 종료 계획 70세면 65~70세다.

활성 일정의 시작은 원천 개시 나이를 유지하고 기간 중첩은 허용한다. 겹친 연금은
엔진에서 더해지며 동일 ID 행만 중복 오류로 잡는다. 기간/금액이 같아도 서로 다른
실제 연금을 중복이라고 지우지 않는다. 순서는 원천 순서를 보존한다.
연금 월액은 **명목 고정액**이며 생활비 물가율을 적용하지 않는다. 은퇴 나이 변경으로
연금 개시를 이동하지 않고 월액·기간·납입 조건을 자동 재산정하지 않는다.

연금 `current_value`, `monthly_savings`, `expected_return_rate`, 가입일·납입기간은
이 매핑에서 사용하지 않는다. 연금계좌 평가·납입·인출을 별도 모델링하지 않고 입력된
월 수령액만 사용한다는 안내를 남긴다. 예상액이 null이면 보고서의 간이 연금식이나
계좌 잔액으로 대체하지 않는다. 납입 중단 등으로 예상 수령액이 달라지는 분석은 미지원이다.

## 5. 미지원 정보의 처리와 결과 경계

| 조건 | 내부 어댑터 처리 |
|---|---|
| `financial_assets`의 `asset_type="기타"` | 해당 행의 자산·적립 합산 제외, `other_financial_asset_not_modeled` 행별 안내. 다른 필수 입력이 유효하면 부분 분석 |
| 6종 밖 미지원 금융자산 분류, 일시금 연금, 모호한 연금 기간, 불완전한 생활비 | 계산 오류. 조용히 제외하거나 일부 행으로 실행하지 않음 |
| `real_estate_assets`에 행 존재 | 유동자산 합계에서 제외. 부동산 평가/처분·임대료·보증금·담보대출이 반영되지 않는다는 안내 필수 |
| `liabilities`에 행 존재 | 부채 원금·이자·상환 현금흐름을 추가 계산하지 않는다는 안내 필수 |
| `goal_milestones`에 행 존재 | 일회성 소득·지출을 월 생활비로 바꾸거나 추가하지 않는다는 안내 필수 |
| 소득·현재 지출, 은퇴 전 목표 | 입력된 금융자산 월 적립 총액을 사용하며 소득-지출/목표를 별도 재계산하지 않는다는 안내 필수 |

처리 결과는 프로필만 반환하고 끝내지 않고, **정형화된 반영 범위 안내**도 함께
반환하는 구조로 구현한다. 안내는 코드·안전한 필드 경로로 표현하고 이름·금액 원문은
포함하지 않는다. 원본 전체를 결과/로그에 보관하지 않는다. 전체 재무상태 분석이 아니라
**지정한 유동 금융자산·저축·생활비·월 연금 범위의 확률**이라는 한계를 항상 남긴다.

2026-09-10 [MVP 정책](simulation-policy.md)에서 이 제한을 안내하는 부분 분석을 허용했다.
부채 상환 등 실제 의무를 반영했다고 표현해서는 안 된다. 필수 누락/미지원 분류의
실행 보류 규칙은 유지하며, 실제 저장 정보의 없음 확인 근거는 BE 연결 전에 확인한다.
최종 서비스가 범위 안내를 버린 채 성공확률만 표시하면 연결 완료로 인정하지 않는다.

## 6. 계산 가정 입력

가정은 고객 snapshot과 별도의 서버 설정 입력이다. 초기 어댑터에서는 다음 다섯
필드를 모두 명시적으로 받는다. 알 수 없는 가정 키는 오타를 숨기지 않도록 거절한다.
내부 모델의 경로 수/시드 기본값이 있더라도 서비스 선택을 암묵적으로 대신하지 않는다.

| 필드 | 단위·검증 |
|---|---|
| `annual_return_mean` | 연 단순수익률의 산술 평균, fraction, 유한 int/float, >-1 |
| `annual_return_volatility` | 같은 수익률의 연 표준편차, fraction, 유한 int/float, >=0 |
| `annual_inflation_rate` | 연 생활비 물가율, fraction, 유한 int/float, >-1 |
| `num_paths` | bool이 아닌 정수 1~100,000. 서비스 허용 상한/성능 보장과 구분 |
| `seed` | bool이 아닌 0 이상 정수. 재현에 필요한 환경/모델 버전은 별도 기록 |

bool·문자열·Decimal·NaN·무한대·null을 자동 변환하지 않는다. percent 입력이 필요한
별도 설정 연결부는 원천 단위를 명시해 100으로 나눈 후 전달해야 하며, 초기 어댑터는
fraction만 받는다. 값의 크기로 단위를 판별하지 않는다. `5`는 내부 계약상 500%이며
5%로 자동 교정하지 않는다. MVP는 아래 고정 정책만 사용하며 사용자 가정 편집은 노출하지 않는다.

BE `DEFAULT_ASSUMPTIONS`에는 `financial_return_rate=0.04`, `inflation_rate=0.02` 등이
있지만 이 설정에는 MC용 포트폴리오 변동성이 없다. BE `_normalize_rate()`의 값 크기
기반 변환을 재사용하지 않는다. 연금의 percent 기대수익률을 포트폴리오 평균/변동성으로
대체하거나 CLI의 0.05/0.10/0.02를 서비스 기본값으로 넣지 않는다.

2026-09-10 [MVP 정책](simulation-policy.md)에서 평균 0.04·변동성 0.10·물가 0.02·
1,000경로·시드 42를 명시적으로 선택했다. 개인별 추정값이 아닌 프로젝트 가정이다.
출처·측정 기간 없음·단위·버전·갱신 정책은 해당 문서를 따르며 엔진의 자동 기본값으로 넣지 않는다.
실제 가정과 모델/매핑 버전은 통합 결과에 포함된다. 별도 정책 버전은 BE envelope에 기록한다.
외부 시장 API는 이번 범위에서 사용하지 않는다. 서버에 검증된 설정이 없으면 실행을
보류하며 CLI 시연값으로 대체하지 않는다.

## 7. 합성 입력과 손계산 기대값

다음은 **필요 필드만 발췌한 저장형 합성 입력**이다. 실제 고객 정보나 BE API 응답
전체가 아니다. serializer의 이름/시각 필드는 생략했다. 추가된 서비스 endpoint도 아니다.

```json
{
  "basic_info": {"age": 40, "retirement_age": 60, "end_age": 90},
  "financial_assets": [
    {"id": 1, "asset_type": "예금/적금", "principal": 90000000, "current_value": 100000000, "monthly_savings": 500000},
    {"id": 2, "asset_type": "펀드/ETF", "principal": 18000000, "current_value": 20000000, "monthly_savings": 250000}
  ],
  "pension_assets": [
    {"id": 1, "receive_method": "연금형", "pension_start_age": 65, "pension_period": "종신", "expected_amount": 1000000}
  ],
  "goal_periods": [
    {"id": 1, "phase": "after", "from_age": 60, "to_age": 74, "items": [{"id": 1, "amount": 1500000}, {"id": 2, "amount": 500000}]},
    {"id": 2, "phase": "after", "from_age": 75, "to_age": 90, "items": [{"id": 3, "amount": 1500000}]}
  ],
  "real_estate_assets": [],
  "liabilities": [],
  "goal_milestones": []
}
```

명시적인 검산 전용 가정은 다음과 같다. 시장 전망/권장값이 아니다.

```json
{
  "annual_return_mean": 0,
  "annual_return_volatility": 0,
  "annual_inflation_rate": 0,
  "num_paths": 2,
  "seed": 7
}
```

기대 프로필은 나이 40/60/90, 자산 **120,000,000원**, 월 적립 **750,000원**,
생활비 **60~74세 2,000,000원/월**, **75~90세 1,500,000원/월**,
연금 **65~90세 1,000,000원/월**이다. 원금 합계나 연금 계좌를 자산에 더하지 않는다.

연 0% 가정에서 40~59세 적립은 `20 × 12 × 750,000 = 180,000,000원`이다.
생활비는 `15 × 12 × 2,000,000 + 16 × 12 × 1,500,000 = 648,000,000원`,
연금은 `26 × 12 × 1,000,000 = 312,000,000원`이다.
최종 계산 잔액은 **-36,000,000원**, 최초 음수 연말은 **85세**다.
84세 연말 0원은 고갈이 아니다. 0 변동성의 두 경로는 동일하므로 성공확률은 **0**이다.
월 적립만 1,000,000원으로 바꾼 What-if는 적립이 60,000,000원 증가해 최종
24,000,000원, 고갈 없음, 성공확률 1, 기준 대비 **+100pp**가 기대값이다.
최초 규격 작성 때는 기존 모델로 직접 검산했다. 후속 기본 테스트는 실제 입력 어댑터를
거쳐 같은 값이 나오는지도 검증한다. 어느 검증도 BE/API 연결 완료의 증거는 아니다.

## 8. 구현 순서·오류·검증 계획

순수 변환 함수와 기본 테스트를 함께 구현했다. 스키마/누락·자료형·
나이/금액 → 금융자산 → 생활비 → 연금 → 내부 모델의 최종 검증 순서로 오류를
일관되게 처리한다. 오류 시 전체 입력 매핑을 실패시키며 부분 프로필로 계산하지 않는다.
오류에는 고정 코드와 `financial_assets[0].monthly_savings` 같은 안전한 경로를 남기고
원문·traceback은 외부로 노출하지 않는다. 외부 HTTP 상태/envelope는 여기서 정하지 않는다.
출력 클래스·기존 `ModelValidationError`의 변환 방식은 입력 어댑터 가이드에 문서화했다.

| 검증 묶음 | 구현 단계에서 추가할 사례 |
|---|---|
| 기본 매핑 | 위 합성 기대 프로필·MC·What-if 검산, 원금/소득/연금잔액 이중 합산 방지 |
| 스키마·금액 | 키 누락/null/0/bool/소수/문자열/음수, 잘못된 행·중복 ID, 알 수 없는 가정 |
| 빈 목록 | 확인 없음/있음, 잘못된 확인 이름·중복·비어 있지 않은 목록과의 모순 |
| 자산·범위 | 모델링 5종·기타 제외/행별 안내·자유 입력 오류, 기타만 있는 입력과 빈 목록 구분, 원본 위치/ID/금액 미사용, 미지원 항목 존재 확인용 목록 누락 |
| 생활비 | 합계·0원·빈 항목·null·정렬·중복·공백·범위 밖 구간 보존·조기 은퇴 전체 교체 |
| 연금 | 종신·N년·기간 경계·계획 밖·복수 중첩·일시금·예상액 없음·납입기간 오용 방지 |
| 가정 | fraction·0 변동성·음수 평균 허용 범위·비유한 값·경로/시드 경계·기본값 미주입 |
| 독립성 | 입력 깊은 복사 비교, 재현성, DB/네트워크/LLM 없이 실행, 기존 계산 테스트 회귀 |

경계 테스트 보강과 합성 저장 입력을 실제 어댑터→MC/What-if로 실행하는
[전용 샘플·사용 가이드](input-samples.md)까지 완료했다. 통합 응답 JSON·성능 측정은 다음 기능 브랜치,
BE 패키징/API·FE 연결은 별도 승인된 작업이다.
