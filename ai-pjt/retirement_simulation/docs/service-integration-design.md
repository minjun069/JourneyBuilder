## 1. 목적과 이번 변경 범위

보고서에서 `시뮬레이션 실행`을 누르면 실제 저장 정보를 바탕으로 몬테카를로를
실행하고, 같은 화면에서 월 저축액·은퇴 나이·은퇴 후 생활비를 바꿔 What-if를
비교한다. 채팅 메시지 입력, Agent 선택, LLM 응답을 실행 전제 조건으로 삼지 않는다.

최초 1단계 작업은 이 문서와 [모듈 README](../README.md)만 변경했다.
후속 입력 어댑터 규격 작업은 같은 모듈 안의 입력 매핑 문서를 추가하고 두 문서를 갱신한다.
계산 코드·BE·FE·AI 공통 서버·DB·의존성·Docker·Compose·CI·Jira는 변경하지 않는다.
문서의 논리 필드와 상태 이름은 구현 제안이며 기존 HTTP 계약의 추가 필드가 아니다.

서비스의 기본 완료 목표는 실제 준비율과 기준 성공확률을 함께 보여주고,
세 가지 What-if 조건으로 기준/변경 결과를 비교하는 것이다. 변경 후 준비율까지
비교할지는 D3에서 별도로 확정한다. 이를 제공하지 않는 범위를 제안서의 모든
준비율 비교 요구까지 완료한 것으로 표시하지 않는다.

시나리오 영구 저장·불러오기, 최적화/추천, 추가 금융상품·주택 처분 시나리오,
LLM 설명은 이번 기본 연결 범위에 넣지 않는다. 임시 실행 상태 보관이 필요해도
사용자 시나리오의 영구 저장 기능과는 구분한다.

## 3. 실행 위치: AI 서버는 필수가 아니다

버튼은 HTTP 요청을 보낼 뿐 Python 모듈을 직접 실행하지 않는다. 실행할 서버는
필요하지만 그 서버가 AI 서버일 필요는 없다. 계산 담당자의 역할과 실행 프로세스의
위치는 별개이며, LLM을 사용하지 않는 계산 모듈도 BE에서 실행할 수 있다.

공통 경계는 `Browser → BE 인증·상담 소유권 검사 → 계산 → BE 응답 → 화면`이다.
Browser가 AI 내부 주소·서비스 토큰을 사용하거나 계산 서버가 업무 DB를 직접
수정하는 경로는 제안하지 않는다.

| 배치 선택지 | 흐름 | 장점 | 필요한 연결/검증 |
|---|---|---|---|
| A. BE에서 패키지 직접 호출 — 사용자 선택 방향 | BE → 입력 어댑터 → Python 계산 함수 → 출력 어댑터 | 별도 내부 HTTP 왕복 없이 기존 인증·보고서 경계 사용. Agent·AI 서버 변경 불필요 | 단일 소스 패키징·BE 이미지 포함·BE 요청 처리 용량·FE 연결 |
| B. 기존 AI 서버에 계산 전용 API — 미선택 비교안 | BE → 인증된 내부 계산 API → 동일 Python 계산 함수 | BE와 계산 프로세스 분리 가능 | 현재 구현 계획에 포함하지 않음. 재선택 시 BE·AI·배포 범위를 새로 확인해야 함 |

현재 [Compose](../../../docker-compose.yml)는 BE를 `backend-pjt/` 컨텍스트로 빌드한다.
[BE Dockerfile](../../../backend-pjt/Dockerfile)에는 `ai-pjt/retirement_simulation/`가 포함되지 않고,
[AI Dockerfile](../../Dockerfile)은 `ai-pjt/`를 복사해 모듈을 포함한다.
따라서 A도 현재 BE에서 import 한 줄로 바로 완성되는 상태는 아니다. 소스를
복제하거나 `sys.path`에 AI 프로젝트 전체를 억지로 추가하지 않고, 모듈의 단일 소스를
패키징/배포하는 방법을 BE·배포 담당 영역에서 결정해야 한다.

A를 기준으로 입력 어댑터와 독립 실행 함수를 준비한다. CPU 계산이 BE 요청 처리를
방해하면 성능 측정 후 BE 실행 격리·호출 제한을 검토한다. 실행 위치를 임의로 B로
바꾸거나 별도 서버·큐·워커를 이번 문서만으로 신설하지 않는다.

B에서 말하는 **AI 공통 진입점 작업**은 새 계산 라우터를 FastAPI 앱에 등록하고
내부 인증·검증을 연결한다는 의미다. 기존 `/chat`, `/v2/chat`, Agent 라우팅·문맥·
매뉴얼을 수정해야 한다는 의미가 아니다. **현재 선택한 A에서는 이 작업을 하지 않는다.**

## 4. 사용자 화면 흐름

```text
보고서 진입
  → 실제 준비율/준비자금과 계산 기준 확인
  → [시뮬레이션 실행]
  → 입력 검증·계산 중 표시
  → 기준 성공확률·자산 범위·최초 자금 부족 분포 표시
  → 월 저축액 / 은퇴 나이 / 기간별 은퇴 생활비 변경
  → [변경 조건으로 비교]
  → 같은 기준 입력·가정·시장 경로의 기존/변경 결과를 나란히 표시
```

### 화면 상태와 표시 규칙

| 상태 | 사용자에게 보이는 내용/동작 |
|---|---|
| 미실행 | 준비율 등 유효한 보고서 정보만 표시. 확률은 `계산 전`, 0%로 대체하지 않음 |
| 입력 부족/미지원 | 부족한 항목 또는 반영 불가 조건과 수정 안내. 숫자를 생성하지 않음 |
| 계산 중 | 버튼의 중복 실행 차단, 진행 상태 표시. 완료 시간은 측정 전 약속하지 않음 |
| 기준 결과 준비 | 준비율과 별도 이름의 `시뮬레이션 성공확률`, 경로 수·기간·가정·계산 기준 표시 |
| 비교 중/준비 | 마지막 유효 기준 결과는 보존. 완료된 동일 배치의 기준/변경 결과로 함께 갱신 |
| 실패/시간 초과 | 실패 원인에 맞는 안내·재시도. 이전 결과는 이전 결과라고 표시하고 새 성공 결과처럼 취급하지 않음 |
| 기준 변경/만료 | 저장 정보·가정·모델 버전 등이 달라졌음을 알리고 재실행. 서로 다른 기준의 결과를 비교하지 않음 |

준비율이 미연결/미정의이면 `준비율 계산 미준비`로 표시하며 고정값을 남기지 않는다.
지원 입력으로 MC만 실행할 수는 있어도 실제 준비율과의 동시 표시 완료로 인정하지 않는다.
차트·패널·모달의 구체적인 레이아웃은 FE 확인 대상이며 현재 화면을 이번에 변경하지 않는다.

### What-if 조건의 의미

- 월 저축액은 기존 대비 증액이 아닌 **변경 후 월 총액**이다. 0은 실제 적립 중단이다.
- 은퇴 나이를 바꿔도 연금 수령 시점이나 생활비 구간을 자동 이동하지 않는다.
- 이미 과거에 은퇴한 사용자의 은퇴 나이 변경은 거절한다. 은퇴 후 저축액 변경은
  현 엔진에서 효과가 없으므로 UI에 안내한다.
- 생활비는 현재 나이 기준 원/월이며 **기간별 전체 일정 교체**다. 조기 은퇴 시
  새로 포함되는 연도까지 명시해야 한다. 단일 숫자로 바꾸는 UI를 택하면 전체 구간을
  그 금액으로 바꾸는지 사용자가 확인할 수 있어야 하며 임의 평균/빈 구간 보충은 금지한다.
- 엔진은 변경안 1~10개를 지원하지만 초기 UI는 기준안+변경안 1개 비교를 우선 제안한다.
  엔진 상한은 서비스에서 허용할 상한이나 응답시간 보장이 아니다.

## 5. 입력 계약 초안

### 5.1 Browser → BE: 실행 의도와 가상 변경값

세션 식별자는 기존 인증된 BE 요청 경계에서 처리한다. Browser가 고객의 원본
재무정보·준비율·성공확률을 권위 있는 값으로 제출하는 계약을 만들지 않는다.
정확한 URL, API 버전, HTTP 응답 envelope는 D2에서 확정한다.

| 논리 필드 | 제안 의미 |
|---|---|
| `mode` | `baseline` 또는 `what_if` |
| `baseline_key` | What-if가 비교할 서버 발급 기준 식별자. 세션 소유권 검사를 대체하지 않음 |
| `changes` | What-if의 세 가지 절대 변경값. 기본 실행에는 변경값을 넣지 않음 |

아래는 **아직 호출할 수 없는 요청 본문 초안**이다. 값은 합성 예시이며,
`baseline_key`는 실제 값이 아니다. 가정·시드는 서버가 선택하고 기록한다.

```json
{
  "mode": "what_if",
  "baseline_key": "example-server-issued-key",
  "changes": {
    "monthly_savings": 750000,
    "retirement_age": 62,
    "retirement_expenses": [
      {"from_age": 62, "to_age": 74, "monthly_amount": 1800000},
      {"from_age": 75, "to_age": 90, "monthly_amount": 1500000}
    ]
  }
}
```

이 예시는 현재 40세·은퇴 60세·종료 90세인 합성 기준 프로필을 전제로 한다.
필드 생략 또는 `null`은 유지, 0은 명시적 변경이다. 빈 생활비 목록은 유지가 아니라
잘못된 전체 교체이므로 거절한다. 알 수 없는 필드·자료형·나이 범위도 거절한다.
미저장 `current_form`과 AI 변경 제안을 병합하지 않고 가상 변경은 계산용 복사본에만 적용한다.

### 5.2 BE → 계산 모듈: 서버가 구성하는 입력

다음은 BE에서 Python 패키지를 직접 호출할 때 유지할 논리 경계다.
원천 코드·최초 지원 범위·정확한 변환/거절 규칙은 [입력 매핑 규격](input-mapping-rules.md)을 따른다.

| 입력 묶음 | 필요한 내용 | 구성 책임 |
|---|---|---|
| 기준 snapshot | `basic_info`, `financial_assets`, `pension_assets`, `goal_periods` 및 미지원 항목 존재 확인에 필요한 정보 | BE: 소유권·저장 상태·동일 시점 검증, 최소 정보 전달 |
| 프로필 | 현재/은퇴/종료 나이, 유동 금융자산, 월 적립 총액, 생활비·연금 일정 | 시뮬레이션 입력 어댑터: 단위·기간·누락 검증 |
| 계산 가정 | 수익률 평균·변동성·물가, 경로 수·시드, 가정 출처/버전 | 서버 정책 및 가정 설정. 시장 기본값은 아직 미확정 |
| 실행 식별 | 기준 식별자, 입력/매핑/모델/가정 버전, 실행 환경 정보 | 서비스 연결부: 같은 비교 기준인지 확인 |
| 변경 조건 | 검증된 세 가지 변경값 | 시뮬레이션 어댑터 → 기존 `WhatIfChanges` |

필드의 기계 원천은 [BE 레지스트리](../../../backend-pjt/consulting/field_registry.py)다.

| 내부 필드 | 원천과 최소 변환 원칙 |
|---|---|
| `current_age/retirement_age/end_age` | `basic_info.age/retirement_age/end_age`; 미입력을 30/60/90 등으로 채우지 않음 |
| `liquid_assets` | 지원하는 `financial_assets[].current_value` 합계. `principal`·연금잔액·부동산과 중복 합산 금지 |
| `monthly_savings` | 해당 금융자산의 월 적립 총액. 소득-지출 잉여와 연금 납입을 다시 더하지 않음 |
| `retirement_expenses` | `goal_periods[phase=after]`의 기간과 `items[].amount`; 총 월 지출의 완전한 비중복 일정 |
| `pension_incomes` | 연금형의 개시 나이·기간·예상 월액. `종신`/양의 정수+`년`의 매핑 규격을 정의했으며 구현은 후속 작업 |

실제 목록의 빈 값만으로 `연금 없음`을 단정하지 않는다. 입력 완료/없음의 근거를
확인하고, 종신·일시금·미입력·불명확한 수령기간을 구별한다. 모호한 기간을 임의의
종료 나이로 바꾸지 않는다. 초기 어댑터는 같은 기간의 항목 금액만 합산하고 서로 다른
생활비 기간의 중복은 거절한다. 빈 목록 확인 근거의 실제 서비스 수집은 D4에 남아 있다.

금액 입력은 원 단위 정수이며 bool을 정수로 받지 않는다. 내부 수익률은 `0.05=5%`다.
BE의 percent 필드를 변환할 때 원천 단위를 사용하며 값 크기로 추측하지 않는다.
연금 기대수익률을 포트폴리오 평균이나 변동성으로 대체하지 않는다.

부동산·부채·일회성 목표·연금계좌 납입/인출은 현재 엔진 지원 범위와 다르다.
초기 어댑터의 계산 보류/범위 안내 규칙은 입력 매핑 문서에 한정해 정의했다.
이를 실제 서비스에 적용하거나 지원 범위를 확대하는 판단은 D4에 남아 있다. 미지원 항목을 조용히
버리고 전체 은퇴 재무상태를 분석했다고 표시하는 처리는 허용하지 않는다.

평균 0.05·변동성 0.10·물가 0.02는 기존 CLI 시연 가정이다. 서비스 기본값이 아니다.
가정의 출처·기간·단위·갱신/버전 정책은 D5에서 결정한다. 외부 시장 API는 필수가 아니며,
필요성이 확인되면 도입 전에 정한다. 브라우저에 자유로운 경로 수/시드 선택은 노출하지 않는다.

## 6. 출력 계약 초안

계산용 출력과 화면용 결합 응답을 분리한다. 계산 모듈은 준비율을 새로 계산하거나
BE 보고서 모델을 참조하지 않는다. 준비율은 별도 검증된 보고서 결과에서 연결한다.

| 계산 출력의 논리 항목 | 원천/의미 |
|---|---|
| 기준 메타데이터 | 기준 식별자, 계산 시각·기간, 입력/어댑터/모델/가정 버전, 경로 수, 실제 경로 출처·시드/RNG·Python 정보 |
| 적용 입력 요약 | 실제 적용한 나이·금융자산·저축·생활비·연금 일정과 반영/제외 범위. 불필요한 원본 개인정보는 제외 |
| 기준 결과 | 성공/고갈 개수·확률, 나이별 잔액 P10/P50/P90, 최초 고갈 나이별 개수·미고갈 개수, 최종 잔액/부족액 분위수 |
| 변경 결과 | 변경값·적용 후 조건과 같은 항목의 계산 결과. 엔진 내부 식별자를 사용자 제목과 구분 |
| 차이 | 성공확률 차이 `pp`, 나이별/최종 잔액 및 최종 부족액 분위수 차이 `KRW` |
| 안내 | 입력/범위 경고, 가정 설명, 모델의 한계. 필수 부족은 성공 경고가 아닌 실행 오류로 처리 |

직렬화에서는 dataclass 필드뿐 아니라 `success_probability` 같은 파생 property도
명시적으로 매핑한다. `asdict()`만으로 화면 계약이 완성된다고 가정하지 않는다.
원시 경로·전체 경로별 현금흐름은 브라우저 응답에 포함하지 않는다.

### 지표·단위와 준비율 연결

- 성공확률은 0~1로 전달하고 화면에서 100을 곱해 `%`로 표시한다. 차이 `pp`는
  이미 `(변경 확률-기준 확률)×100`이므로 다시 100을 곱하지 않는다.
- 성공은 계획 기간 중 **연말** 잔액이 한 번도 음수가 되지 않은 경로다. 0은 고갈이
  아니며 중간 고갈 후 회복도 실패다. 현실의 성공 보장이나 연중 지급능력 보장이 아니다.
- 금액 결과는 유한한 명목 KRW다. 화면 반올림은 표시만 바꾸며 계산/판정을 바꾸지 않는다.
  브라우저의 안전한 숫자 범위를 넘는 금액과 JSON 비유한 값의 처리는 출력 어댑터에서
  명시적으로 검증하며, 정밀도 손실을 묵인하거나 임의로 잘라내지 않는다.
- 자산 P10/P50/P90은 자산 분포이며 성공확률의 신뢰구간이 아니다. 분위수 차이는
  각 결과 분위수의 차이이지 경로별 차이의 분위수가 아니다.
- 고갈은 나이별 분포와 미고갈 개수로 먼저 보여준다. 고갈이 없는데 임의의 고갈 나이를
  만들지 않는다. 대표 나이를 추가하려면 고갈 경로 조건부 여부·동률 처리까지 별도 정의한다.
- 준비율은 현재/은퇴 시점의 어떤 자금과 어떤 필요자금을 비교하는지 D3에서 정한다.
  `total_retirement_assets / total_required_fund`를 검토 없이 확정 공식으로 사용하지 않는다.
  분모 0·미입력·100% 초과의 표시 정책도 정하고 준비율을 성공확률로 대체하지 않는다.
- BE 계산에는 부동산·연금 평가액 등이 포함되지만 현 MC는 유동 금융자산/현금흐름
  모델이다. 같은 snapshot이어도 자산 범위·가정·시점이 다를 수 있음을 설명한다.
- 변경 후 준비율을 제공한다면 BE 측에서 가상 조건으로 재계산할 수 있어야 한다.
  `generate_sync_report()`는 보고서 버전을 저장하므로 What-if의 임시 계산에 그대로
  사용하지 않는다. 원본 폼 저장 후 복구하거나 BE 공식을 AI 쪽에 복제하지 않는다.

### 기준안의 일치와 개인정보

What-if는 매번 기존 `calculate_what_if()`로 기준/변경안을 한 배치에서 계산하고
배치의 기준 결과까지 함께 반환하는 방식을 우선 제안한다. 이전 화면의 확률과
새 시장 경로의 변경 결과를 그대로 빼지 않는다. 같은 기준 재현에는 입력·어댑터·
가정·경로 수·설정 시드·모델·실행 환경이 같아야 하며 실제 난수 미사용 상태도 보존한다.

`baseline_key`는 이 조건을 확인하는 서버 측 식별 수단의 초안이다. 발급/검증,
동일 시점 읽기, 만료/재배포 시 무효화, 소유권 확인 방식은 D2에서 결정한다.
재무정보 원문이나 단순 재무값 해시를 공개 식별자로 사용하지 않는다. 보고서 버전만으로
원천 재무정보가 동일하다고 가정하지 않으며 오래된 보고서와 최신 MC를 조용히 결합하지 않는다.

## 7. 오류·자원·서비스 경계

| 오류 분류(제안) | 처리 |
|---|---|
| 인증/소유권 실패 | BE에서 차단. 엔진 실행·타 사용자 정보 노출 금지 |
| 입력 부족/유효성 실패 | 안전한 필드 경로·안내 반환. 미입력과 0 구분 |
| 지원 범위 밖 | D4의 안내/보류 정책 적용. 미지원 조건을 몰래 다른 값으로 치환하지 않음 |
| 기준 변경/만료 | 재실행 안내. 다른 기준과 비교 결과를 성공으로 반환하지 않음 |
| 가정 미준비 | 시연값으로 fallback하지 않고 실행 보류 |
| 실행 한도/과부하/시간 초과 | 서비스가 정한 제한과 재시도 가능 여부 안내 |
| 수치/내부 오류 | 기존 엔진의 전체 실패 원칙 유지. 일부 경로 제외·부분 비교 결과로 성공 처리 금지 |

`ModelValidationError`, MC/What-if 수치 오류를 외부 오류로 변환하되 traceback,
금액 원문, 고객 객체, 서비스 토큰을 응답/일반 로그에 넣지 않는다. 기존 채팅 오류
코드나 timeout을 새 계산 계약에 임의로 재사용하지 않는다.

재시도는 동일 실행의 중복 계산과 충돌을 구분해야 한다. 브라우저에서 버튼을 막는
것만으로 서버 중복 방지가 완성되지 않는다. 경로 수·기간·동시 실행·재시도 한도와
성능 목표는 작은 사례부터 측정한 뒤 D6에서 확정한다. 엔진의 100,000 경로·10개
변경안 상한을 그대로 공개 API 최대치로 채택하지 않는다.

동기 응답으로 충분하면 작업 큐·polling을 추가하지 않는다. 비동기가 필요하면
작업 ID·상태·만료·소유권·취소 시 실제 계산 중단 여부를 별도 설계하고, 연결 종료를
CPU 작업 취소와 동일하게 취급하지 않는다. 본 문서에서 새 인프라를 도입하지 않는다.

## 8. 담당 경계와 협의 체크리스트

**4단계는 연결 코드를 구현하는 시점이지 협의를 처음 시작하는 시점이 아니다.**
이번 문서를 1단계의 확인 자료로 공유할 수 있으며, 독립 모듈에 영향이 없는 구현은
계속하되 생산자/소비자가 함께 사용할 계약은 연결 전에 확정한다. 아래 담당은 역할
제안이고 실제 팀원의 수락이나 작업 배정을 의미하지 않는다.

| 작업 | 시뮬레이션 담당 영역 | 확인/연결이 필요한 다른 영역 |
|---|---|---|
| 입력 매핑·계산·결과 변환·전용 테스트 | 주 구현 | 원천 필드 의미는 BE, 표시 필요 필드는 FE 확인 |
| 준비율 정의·실데이터 연결 | 차이/한계 문서화, MC와 기준 일치 검증 | 기존 BE 계산·FE 표시 담당 |
| 선택한 BE 직접 실행 방식 | 패키징 가능한 독립 모듈 제공 | BE 호출·패키지 배포·자원 한도, FE API/화면 |
| AI 서버 공통 진입점·Agent·컨텍스트·상담 매뉴얼 | 수정하지 않음 | 현재 연결 계획의 변경 대상 아님 |

|---|---|---|---|
| D1 | BE 직접 실행의 단일 소스 배포·호출 담당 | BE·배포 | 실행 위치는 사용자 선택 완료. 패키징·구현 범위 승인·담당 확인은 연결 전 필요 |
| D2 | 요청/응답·URL·버전·완료 상담 정책·동일 snapshot/기준 식별/만료 | BE·FE | 논리 초안은 본 문서, 외부 계약 구현 전 필수 / 미확정 |

| D5 | 평균·변동성·물가 출처/버전·갱신·반영 범위, 외부 API 필요 여부 | 기능 담당, 데이터/설정 연결 담당 | 명시적 fraction 입력·자동 기본값 금지는 정의. 실제 시장 가정/출처는 미확정 |
| D6 | 성능 목표·동기/비동기·시간 제한·동시성·중복 실행·재시도 | 실행 서버·배포·FE 담당 | 측정 결과 확인 후 API 완료 전 / 미확정 |

정식 회의가 필수인 것은 아니다. MD에 대한 확인이나 기존 팀 계약의 재사용으로도
정할 수 있다. 다만 문서 작성만으로 합의가 된 것은 아니며, 회신이 없다는 이유로
BE·FE·공통 서버의 변경 권한을 추정하지 않는다. 전혀 확인하지 않는 경우에는
독립 어댑터·합성 검증까지와 실제 서비스 연결 완료를 구분한다.

| 1 — 문서화 완료 | 화면 흐름·입출력·배치 선택·협의 항목 문서화 | 문서/README 정합성·링크 검증. 외부 계약 동결과 구분 |
| 2 — 규격 작성, 구현 전 | 실제 입력 매핑·가정 규격 및 어댑터 | 실제 스키마 형태의 합성 fixture, 누락/0/단위/기간/미지원 회귀 테스트 |
| 3 | 통합 실행 함수·출력 변환·성능 검증 | 기준/What-if JSON 매핑, 공통 경로·재현성, 시간/메모리 측정과 한도 근거 |
| 4 | BE 직접 실행·패키지 배포·인증된 계산 요청 연결 | 사용자/세션 소유권·완료 상담·기준 변경·오류·중복/시간 제한 API 테스트 |
| 5 | 실제 준비율과 기본 MC 화면 연결 | 고정값/mock 없이 실제 입력에서 두 지표 표시, 단위·가정·차트 확인 |
| 6 | What-if UI·동일 배치 비교 연결 | 세 조건·생활비 coverage·과거 은퇴 제한·원본 불변·오래된 응답 방지 |
| 7 | 통합·배포 환경 검증 및 인수 문서 | 저장→보고서→실행→비교 E2E, 격리/실패/재시도, 배포 성능·운영/사용 가이드 |

단계 2는 저장 원천을 읽는 코드를 무조건 먼저 변경한다는 뜻이 아니다. 합의된
snapshot을 받는 순수 어댑터부터 구현하며 D4/D5의 미결정을 샘플값으로 숨기지 않는다.
단계 4~6은 해당 영역의 변경 범위가 승인되거나 담당자가 연결하는 것을 전제로 한다.

### 서비스 인수 체크

- [ ] 실제 저장 정보와 계산 기준이 화면에 표시되고 개발 mock/고정 준비율을 사용하지 않는다.
- [ ] 준비율의 정의·원천·계산 시점이 확정되어 성공확률과 구분된다.
- [ ] 채팅/LLM 없이 버튼으로 계산된다. BE 직접 실행으로 AI 서버 없이도 해당 기능의 동작을 검증한다.
- [ ] 기본 MC와 What-if가 동일 기준으로 재현되고, 성공확률·금액·pp가 원천 결과와 일치한다.
- [ ] 생활비 전체 교체, 조기/이미 은퇴, 연금 없음/미입력, 음수 잔액과 고갈 없음이 검증된다.
- [ ] 원본 재무정보·보고서 버전·AI 대화 컨텍스트를 What-if 실행으로 수정하지 않는다.
- [ ] 인증·세션 격리·중복 요청·시간 초과·기준 변경·늦게 도착한 응답을 안전하게 처리한다.
- [ ] 실제 배포 환경에서 성능과 가정 설정을 확인하고, 한계·실패 대응·사용 방법을 문서화한다.
- [ ] D3에서 변경 후 준비율을 포함했다면 원본 저장 없는 재계산·비교까지 검증한다.

현재 서비스 인수 항목은 미완료다. 기존 모듈의 300개 단위 테스트 완료 기록은
[What-if 샘플 가이드](what-if-samples.md)에 있으며, API·FE·배포 통합 검증을 대신하지 않는다.

## 10. 최초 서비스 설계 문서 작업의 검증 기록

2026-09-09, Miniforge `retirewise-ai`에서 확인했다.

- README와 이 문서의 로컬 링크 43개(기존 anchor 포함), 제목 주변 빈 줄·코드 블록·
  후행 공백을 검사했다.
- 5.1절의 JSON 예시를 파싱하고 기존 합성 기준 프로필에 `WhatIfChanges`로 변환해
  적용했다. 나이·월 적립·생활비 일정, 연금 일정 유지, 입력/기준 프로필 불변을 확인했다.
  이 검증용 변환은 제품용 입력 어댑터나 HTTP API 구현이 아니다.
- D1~D7 항목이 각각 한 번 정의되어 있는지 확인했다.
- 기존 계산 모듈 테스트 **300개 통과**. 재실행 명령은 저장소 루트에서 다음과 같다.

```bash
conda run -n retirewise-ai python -S -B -m unittest discover -s ai-pjt/retirement_simulation/tests -q
```

새 API·FE·배포 통합 테스트는 실행하지 않았다. 런타임 코드를 변경하지 않은
설계 문서 작업이며, 위 서비스 인수 체크리스트의 미완료 상태는 유지된다.
