# 시뮬레이션 전달 묶음과 남은 작업 순서

2026-09-10. `feat/ai-simulation-handoff`, 시작 기준 `master=d39677b`, MR 준비 시 rebase 기준 `991521c`.
사용자가 기능/정책을 결정하고 전달 준비를 요청한 범위다. **실제 담당자 전달·기술 합의·서비스 연결은 미완료**다.
현재 FE 담당자는 없다. 아래 FE 자료는 향후 화면 구현자를 위한 규격 초안이며, 사용자나 다른 팀원에게
화면 작업을 배정했다는 뜻이 아니다. 이번 요청은 푸시·MR 생성까지이며 **병합은 진행하지 않는다.**

## 1. 이번 브랜치에서 제공하는 것

| 읽을 사람 | 우선 전달할 자료 | 용도 |
|---|---|---|
| 전체 | [MVP 정책](simulation-policy.md) + [정책 JSON](simulation-policy.json) | 4%/10%/2%·1,000경로·시드 42, 변경 후 준비율 제외, 안내를 유지한 부분 분석 |
| BE·배포 | [BE 인수인계](be-handoff.md) + [설치 가이드](package-installation.md) | 패키지 직접 import·snapshot/가정 연결·오류·설치/버전/해시 |
| 기능 담당·BE / 향후 화면 구현자 | [기술 확인서](be-integration-checklist.md) | 기능을 다시 논의하지 않고 담당자·API·원천·운영 정책의 남은 답변 확인 |
| 향후 화면 구현자(현재 미정) | [화면 연결 안내](fe-handoff.md) + [전체 합성 JSON](handoff-examples.json) | 조건 편집·결과 필드·단위·상태/오류·범위 안내 |
| 검증 담당 | [검증 기록](handoff-validation.md) + [원시 결과](handoff-validation-results.json) | 7조합·시드/경로 수·가정 민감도·재현/실패 사례 |

자료만 필요하면 위 링크를 전달한다. 설치가 필요하면 선택한 소스 커밋에서 빌드한 wheel과
별도 빌드 보고서/SHA-256, 정책 JSON도 함께 제공한다. 실행 가능한 wheel은 Git에 넣지 않는다.
소스 커밋/정책 버전/실제 설치 파일 해시를 구분하고, 문서의 임시 디렉터리를 배포 위치로 사용하지 않는다.
단일 소스 런타임 18개와 공개 인터페이스는 그대로이며 docs/tests만 소스 배포에 추가했다.

### 검증된 범위

- 기존 643개 + 인수인계 25개 = 소스 테스트 **668개**, 일반 Python과 `-S` 실행 모두 통과.
- 고정 행렬 **37회** 완료: 3종 합성 입력 × 2경로 수 × 5시드 + 단일 가정 변화 7회.
- 두 번째 작업의 스테이징 tree `7da364ec5113222b3e4e2749afe5ed859c67fb97`에서
  sdist→wheel 빌드, 소스 자료 포함 및 wheel의 런타임 18개 일치 확인.
- 해당 빌드: wheel 22개 파일 / sdist 94개 일반 파일. 격리 설치 **14개** 검사 통과.
  후속 문서 추가로 최종 sdist 파일 수/해시는 달라지며 과거 빌드를 같은 산출물로 취급하지 않는다.
- 설치용 wheel에는 docs/tests·정책 JSON이 없으며, 정책 로딩·API·FE 연결은 구현하지 않았다.

검증은 합성 입력/로컬 CPython 3.13.15 기준이다. BE 이미지 3.13.14·원화 시장 보정·
인증/동시성·실제 고객 E2E가 완료되었다고 해석하지 않는다.

## 2. 지금 다음으로 할 일

1. 최신 master 위로 rebase하고 검증한 뒤 이 브랜치를 푸시·MR 생성한다. 작성자/할당자는 이지석으로
   확인하며 병합·자동 병합은 설정하지 않는다. 연결 브랜치에서 사용할 소스 커밋/아티팩트는 별도로 고정한다.
2. 사용자가 BE 담당에게 자료를 전달하고 기술 확인서 Q1~Q6과 Q7의 준비율 원천/응답 부분을 확인한다.
   설치/API 담당, 동일 snapshot/없음 확인, URL/envelope/오류·기준 만료·실행 보호를 기록한다.
   FE 담당 부재를 API 계약 확인의 선행 장애로 두지 않으며 화면 레이아웃/구현 책임은 아직 확정하지 않는다.
3. BE 담당이 확정된 계약에 맞춰 별도 브랜치에서 이미지 설치·정책 설정·인증 API를 연결한다.
   시뮬레이션 담당은 모듈 결과 검증/필요한 순수 매핑 보완을 맡는다. 먼저 API 테스트로 기준/변경 1개,
   단위·원본 보존·권한/오류·기준 만료를 검증한다. FE 없이 가능한 완료 범위는 **BE/API 연결**까지다.
4. 화면 구현 담당과 수정 범위를 정한 뒤 보고서 버튼·결과 표시·세 조건 편집을 별도 브랜치에서 연결한다.
   사용자가 직접 맡는다면 그때 시뮬레이션 관련 FE 변경을 명시적으로 승인받는다. 담당 미정이면 화면 작업은
   대기하되 BE/API 인수는 계속할 수 있다. 모듈 설치만으로 화면이 생성되지는 않는다.
5. 화면 연결 후 실제 저장→보고서→기준/변경 비교 E2E와 실제 BE 부하·timeout·배포 검증을 마친다.
   API 테스트나 화면 mock만으로 서비스 전체 완료라고 표시하지 않는다.

문서 작성/전달만으로 회신이나 변경 권한이 생기지 않는다. 시뮬레이션 담당은 BE·FE 파일을 임의 수정하지 않는다.

## 3. 서비스 완성까지

| 순서 | 주 담당 | 작업 / 완료 기준 |
|---|---|---|
| A. 기술 계약 확인 | 기능 담당 + BE | Q1~Q6 및 Q7 원천/응답 확인. 화면 구현 담당·UI 확인은 별도 미결 항목으로 유지 |
| B. BE 이미지/설정 | BE·배포 | wheel 출처·버전/해시 고정, 일반 설치, 실제 이미지 import·가정 설정 검증. AI 프로젝트 전체 복사 금지 |
| C. BE 실행 API | BE | 인증/소유권·상담 상태·일관된 snapshot·없음 확인·가상 변경·기준 키/만료·실패·동시/중복 제한 |
| D. FE 화면 | 미정 → 담당/범위 확정 후 착수 | 보고서 실행·기준+변경 1개·조건 3종·실제 준비율/미준비·단위/차트·안내·로딩/오류/늦은 응답 |
| E. 통합 인수 | BE + 확정된 화면 구현자 + 시뮬레이션 담당 | 실제 저장→보고서→실행→비교, 입력/정책/환경 기준 일치·원본 보존·오류/만료·mock 제거 |
| F. 운영/배포 | BE·배포 + 확정된 화면 구현자 | 실제 기간·정밀도·동시 부하·취소/timeout·배포 버전·비식별 로그·배포 후 재확인 |

A를 마치면 B/C와 API 단독 검증을 먼저 진행한다. D는 담당/수정 범위가 정해진 경우에만
합의한 JSON을 기준으로 병행할 수 있다. 큐/별도 AI 서버를 먼저 만들지 않고 실제 BE 성능/운영 요구에
따라 별도 승인 범위에서 실행 격리를 선택한다. 기간·경로를 몰래 줄이지 않는다.
확정한 1,000경로 정책에 정밀도 요구가 맞지 않으면 추가 경로 검증 후 정책 버전을 올린다.

## 4. 완료와 미완료를 구분

- **모듈 전달 준비 완료:** 독립 계산/패키지·정책/범위·재현 샘플·회귀·설치 검증·담당별 자료.
- **미완료:** 담당자 회신, BE 설치/API/운영 정책, 화면 구현 담당 확정·실데이터 화면, 실제 입력 E2E와 배포 확인.
- **이번 범위 밖:** 변경 후 준비율, 최적화/추천, 시나리오 영구 저장, LLM 설명, Agent·컨텍스트·매뉴얼.

다른 AI 담당과의 기능 중복 없이 진행할 수 있지만 서비스 완료에는 BE·FE 연결이 필요하다.
기존 준비율 원천이 준비되지 않으면 MC 단독 동작과 두 지표 표시 완료를 구분한다.
