## 3. 측정 방법과 보호 장치

### 시간

`measure_timing()`은 같은 사례를 1회 전체 실행해 warm-up한 뒤 3회 측정한다. 각 반복 전에
명시적 GC를 수행하지만 측정 창에서는 GC를 끄지 않는다. 이전 반복의 결과/bytes를 해제한다.
`time.perf_counter()`로 아래 네 값을 초 단위로 기록한다.

| 값 | 포함 | 제외 |
|---|---|---|
| `analysis_s` | `analyze_retirement()`: 저장/가정/변경 매핑·프로필 검증·경로 생성·기준/변경 계산·집계·결과 모델 | 입력 fixture 생성·조회·프로세스 시작/import·warm-up |
| `conversion_s` | `analysis_to_dict()`: 숫자/정합성 재검증·전체 dict/list 변환 | JSON 인코딩·FE 표시 |
| `encoding_s` | `json.dumps(ensure_ascii=False, allow_nan=False, separators=(',', ':'))`와 UTF-8 bytes 변환 | 네트워크 전송·HTTP/프레임워크 응답 처리 |
| `total_s` | 위 세 작업을 연속 실행한 첫 시각~마지막 시각 | 사후 JSON 역직렬화·결과 검사·SHA-256·출력·측정 통계 |

전체 중앙값은 **각 실행의 전체 시간 중앙값**이지 세 구간 중앙값을 합산한 값이 아니다.
원시 기록에는 세 표본과 구간별 min/median/max를 남긴다. 표본 3개의 최대값을 P95/P99나 SLA로 부르지 않는다.

### 메모리

시간 측정에는 `tracemalloc`을 켜지 않는다. `measure_memory()`는 별도의 새 프로세스에서 같은 사례로
warm-up한 뒤 `tracemalloc.start(1)`을 켜고 **1회** 실행한다. 추적 중 실행 시간은 정상 성능 수치에 섞지 않는다.

- 각 단계의 `start_bytes`·`end_bytes`·`peak_bytes`와 `incremental_peak_bytes = peak - start`를 기록한다.
  다음 단계 전에 peak만 초기화하므로 dict 변환은 결과 모델을, 인코딩은 모델과 dict를 보유한 상태다.
- `pipeline_peak_bytes`는 세 단계 peak의 최댓값이다. 단계 peak나 RSS를 합산하지 않는다.
- 추적은 fixture/import/warm-up 후 시작하고 사후 역직렬화/해시 검증 전에 끝난다.
  Python 할당 추적이며 모든 native 메모리·allocator arena·프로세스 전체를 포괄하지 않는다.
  단계별 기록 객체와 계측 자체의 소량 할당은 포함될 수 있다.
- Linux `ru_maxrss`는 KiB→bytes로 변환해 시간/메모리 worker별로 기록한다. 이는 **프로세스 생애 최고 RSS**라
  import·warm-up·사후 검증도 포함하며 요청별 증가량이 아니다. 다른 OS는 단위를 추정하지 않고 null로 남긴다.
  메모리 worker RSS에는 추적 도구 비용도 포함된다.
- 기존 tracing 또는 비활성 GC 상태에서는 임의로 전역 상태를 바꾸지 않고 측정을 거절한다.
  메모리 측정 중 실패해도 tracing을 종료한다.

### 결과 확인과 실행 제한

각 표본의 엄격한 JSON round-trip·경로 수·기간·시나리오 수·모드·안내를 확인한다. 시간 표본끼리,
그리고 시간/메모리 worker 간 인코딩 bytes 길이와 SHA-256이 같아야 성공한다.
기록에는 실제 금융 결과값이나 프로필을 넣지 않으며 이 해시는 합성 fixture 결과에만 사용한다.

- CLI는 내장 사례 **하나씩** 실행한다. 기본은 10경로·11년의 `smoke_baseline`이다.
- 사례의 도구 상한은 경로 5,000개·기간 81년·비교안 10개 및
  `N × T × (S+1) ≤ 600,000`이다. 기준안도 1개로 계산한다.
- 시간 worker와 메모리 worker는 **순차 별도 subprocess**이며 각각 기본 45초 timeout이다.
  시간 표본 수는 1~5, worker timeout은 1~60초로 제한한다. timeout은 측정 도구의 보호 장치이지 HTTP 정책이 아니다.
- 실패/timeout이면 해당 실행의 정상 전체 보고서를 내보내지 않는다. 후속 worker를 계속 실행하지 않는다.
  timeout은 `subprocess.run()`이 해당 자식 프로세스를 종료·회수한다. 도구는 손자 프로세스를 만들지 않는다.
- 작업량 상한은 제한된 사례의 실수 방지용이며 OS 메모리 hard limit이나 악의적 입력 격리가 아니다.
  내부 `--_worker`는 부모 실행기용이며 직접 실행하면 부모 timeout 보호가 없다.
- **기존 엔진의 100,000경로·10개 변경안 상한, 서비스 입력 계약이나 API 설정은 변경하지 않았다.**

### 관측 해석과 코드 근거

- T=31, S=1에서 N=100→1,000→5,000이면 전체 약 25.6→240.8→1,237.4ms,
  추적 peak 약 0.258→2.313→11.380MiB다. 원시 경로/잔액 크기가 경로 수에 따라 늘어난다.
- N=1,000, S=1에서 T=11→31→51→81의 전체 시간은 약 84.1→240.8→403.6→644.0ms다.
- N=1,000, T=31에서 S=0→1→3→10의 전체 시간은 약 121.7→240.8→478.2→1,376.1ms다.
  [What-if 엔진](../what_if_engine.py)은 시장 경로를 공유하지만 **각 변경의 현금흐름 계산은 별도로 실행**한다.
- [경로 생성기](../return_paths.py)는 `O(N×T)` 수익률을 보유하고,
  [MC 엔진](../monte_carlo.py)은 나이별 잔액 표본과 정렬된 복사본을 사용한다.
  고정된 입력 일정 수에서 계산/정렬 비용은 대략 `O((S+1)×T×N log N)`이며, What-if의 경로 재검증도 포함된다.
  현재는 변경안들을 순차 계산해 대략 `O(N×T + S×T)`의 주요 저장량을 사용한다.
  이는 코드 구조 설명이지 실행시간/메모리 상한 보장이 아니다. 입력 일정 수가 늘면 검증/현금흐름 비용도 늘어난다.
- JSON에는 경로 전체가 아닌 요약만 담긴다. N 변화에 비해 변환 시간과 bytes 크기 변화가 작고,
  T·S가 늘면 출력 행과 크기가 늘어난다. 대표 사례에서 비용의 대부분은 계산이며 JSON 최적화를 우선할 근거는 약하다.
- 변동성 0에서도 모든 경로를 기존 방식으로 계산한다. 빠르다는 이유로 중복 경로 생략·추정 결과·
  조용한 경로 수 축소·기준 결과 재사용 등의 최적화를 추가하지 않았다. 계산 규칙과 재현성을 유지한다.

## 5. 초기 연동 후보 한도와 미검증 범위

**연동 성능 시험은 N≤1,000, T≤51, S≤3에서 시작하는 것을 권장한다.**
대표 교차점의 작업량은 `1,000×51×4 = 204,000 path-year evaluations`다.
같은 환경의 측정값을 근거로 삼은 **시험 후보 범위**이지 이 직사각형 안 모든 입력의 성능 보증은 아니다.
표의 다른 측정점도 통과했지만 예를 들어 N=5,000·T=81·S=10의 조합은 측정하지 않았다.

| 구분 | 제안 / 근거 / 남은 확인 |
|---|---|
| 경로 수 | 초기 시험 1,000개. 시드·가정을 명시하고 비교안 전체에 공통 시장을 사용. 표본 수의 통계적 충분성 검증과 성능 검증은 별도 |
| 기간 | 초기 시험 최대 51년. 실제 고객의 종료 나이를 잘라내지 않는다. 초과 입력은 별도 성능 검증/처리 정책 필요 |
| 비교안 | 초기 시험 최대 3개. 월 적립·은퇴 나이·생활비 변경의 실제 조합과 복잡한 일정도 BE 환경에서 추가 측정 |
| 동시성 | 목표 BE 이미지에서 우선 동시 계산 1개로 재측정 후 경쟁 부하 시험. 논리 CPU 22개를 그대로 worker 수로 사용하지 않음 |
| timeout·취소 | 요청 timeout이 동기 Python 계산 자체를 중단한다고 가정하지 않음. 서비스의 실행 격리·취소/중복/재시도 정책은 별도 설계 |
| 운영 제한 적용 | 이 단계에서는 **문서 제안만** 한다. 경로/기간/변경안 및 원천 행 수의 서버측 검증·HTTP 응답·큐/프로세스 설정을 변경하지 않음 |

입력을 무시하거나 종료 기간·경로·변경안을 조용히 줄여 응답시간을 맞추지 않는다.
100,000경로·10개 변경안은 기존 모델의 허용 상한이지 브라우저 요청에 허용할 운영 값이 아니다.

아직 검증하지 않은 항목:

- 운영 BE 컨테이너의 실제 CPU/RAM 제한·프레임워크/ORM·콜드 스타트·네트워크·DB 조회·API 동시 부하.
- 모든 나이 조합(예: 18~120세의 103년), 최대 경로/기간/시나리오의 결합, 다양한 시드·금융 가정.
- 많은 금융자산/연금/생활비 행·복잡한 기간·대규모 입력 검증·오류 경로의 자원 사용량.
- 장시간 soak·메모리 누수·P95/P99·동시성·timeout·작업 취소/복구·서비스 처리량.
- 시장 보정/상관관계·성공확률의 정밀도. 성능 때문에 0%/100%를 보장으로 표시하지 않는다.

BE 직접 실행 방향은 유지하며 별도 AI 서버나 Agent를 만들지 않는다. 관련 운영 결정은
[서비스 연결 설계](service-integration-design.md)의 D1/D6 등과 함께 연결 전에 확정해야 한다.

## 6. 재실행·회귀 검증·남은 순서

저장소의 `ai-pjt/`에서 작은 사례를 먼저 실행한다. 표준 출력은 벤치마크 JSON 1개이며 파일을 자동 저장하지 않는다.

```bash
conda run -n retirewise-ai python -S -B -m retirement_simulation.analysis_benchmark
conda run -n retirewise-ai python -S -B -m retirement_simulation.analysis_benchmark --case smoke_what_if
conda run -n retirewise-ai python -S -B -m retirement_simulation.analysis_benchmark --case n1000_y51_s3 --repeats 3 --timeout 45
```

전체 14개를 재측정하려면 같은 환경/디렉터리에서 아래를 실행한다. 결과는 줄마다 독립된 JSON이다.
소규모 확인 후 실행하며 시간이 오래 걸리면 종료하고 자원 상황을 확인한다. 이번 기록은 이 순서로 수집했다.

```python
import json
from retirement_simulation.analysis_benchmark import CASES, run_benchmark
for name in CASES:
    report = run_benchmark(name, repeats=3, timeout=45)
    print(json.dumps(report, ensure_ascii=False, allow_nan=False, sort_keys=True), flush=True)
```

메모리 측정은 느리므로 큰 행렬을 일반 단위 테스트마다 실행하지 않는다.
